# 技术栈统一改造开发计划

## 1. 项目背景

当前后端使用 Spring Data JPA、内存 Session 和手写权限判断，前端为 Vue 3 + TypeScript + Vite。

本次改造目标：

- 统一使用 MyBatis-Plus，移除 JPA/Hibernate；
- 启用 Redis，承载登录 Session、权限缓存和分布式能力；
- 建立标准化 RBAC 权限模型；
- 保持现有前端主要 API 格式和业务流程稳定；
- 保证每个阶段可独立验证、可回滚。

## 2. 目标技术栈

| 领域 | 目标技术 |
| --- | --- |
| 前端 | Vue 3、TypeScript、Vite、Pinia、Vue Router |
| 后端 | Java 21、Spring Boot 3.4、Spring Web |
| 持久层 | MyBatis-Plus、MySQL |
| 数据库迁移 | Flyway |
| 认证授权 | Spring Security 6、Bearer Token、标准 RBAC |
| 缓存与分布式能力 | Redis、Spring Data Redis |
| 文档解析 | Apache PDFBox、Apache POI |
| 自动化执行 | Jenkins、Allure |
| 测试 | Spring Boot Test、JUnit、MockMvc、MySQL/Redis 集成测试 |

## 3. 改造原则

1. **先基础设施，后业务迁移**：先完成依赖、配置、数据库和 Redis 能力，再迁移业务模块。
2. **一次只保留一套持久层**：迁移完成后删除 JPA/Hibernate，避免长期双轨维护。
3. **权限以后端为准**：前端只负责展示控制，后端必须独立完成权限校验。
4. **数据结构由 Flyway 管理**：不使用 ORM 自动建表，所有结构变更都提供版本化迁移脚本。
5. **每阶段可验收**：每一阶段都必须有代码、测试、配置和回滚说明。
6. **兼容现有 API**：除非确有必要，不改变前端现有请求路径、响应包装和 Bearer Token 形式。

## 7. 阶段 2：数据库与标准 RBAC 模型

> 状态：已完成（2026-08-22）。验收记录见《阶段2-数据库与标准RBAC模型验收记录》。

### 目标

将当前字符串角色和分散权限判断升级为数据库驱动的标准 RBAC。

### 7.1 新增数据表

建议新增以下表：

```text
roles
permissions
role_permissions
user_role_assignments
```

主要字段：

```text
roles
- id
- code
- name
- scope_type       SYSTEM / PROJECT
- enabled
- created_at
- updated_at

permissions
- id
- code
- name
- resource
- action
- enabled

role_permissions
- role_id
- permission_id

user_role_assignments
- id
- user_id
- role_id
- scope_type
- scope_id
- created_at
```

### 7.2 角色设计

系统角色：

- `ADMIN`
- `TEST_DEVELOPER`

项目角色：

- `PROJECT_OWNER`
- `PROJECT_MANAGER`
- `PROJECT_TEST_DEVELOPER`
- `PROJECT_VIEWER`

### 7.3 权限设计

权限编码采用 `资源:动作` 格式，例如：

```text
system:user:manage
system:role:manage
system:ai-model:manage
system:jenkins:manage
project:read
project:update
project:member:manage
requirement:read
requirement:write
testcase:read
testcase:write
testcase:review
api:execute
automation:execute
report:read
ai:generate
ai:analyze
```

### 工作内容

- 新增 Flyway RBAC 迁移脚本；
- 初始化角色和权限；
- 将现有管理员和项目 Owner 映射到新授权表；
- 为旧角色字段保留兼容读取窗口；
- 建立角色、权限和授权关系的 Mapper；
- 实现 `RbacService`；
- 实现系统级和项目级权限查询；
- 增加唯一约束，避免重复授权；
- 增加权限变更审计日志。

### 验收标准

- 新旧用户都能完成角色迁移；
- 系统角色和项目角色可以独立授权；
- 同一用户在不同项目中可以拥有不同项目角色；
- 权限查询结果可追踪到角色和权限表；
- 权限变更有操作审计记录；
- Flyway 可在空库和已有库上成功执行。

### 回滚点

- 新表采用新增方式，不立即删除旧角色字段；
- 保留旧字段到阶段 5 验收结束；
- 迁移失败时可回退授权读取逻辑，不影响业务主表。

## 8. 阶段 3：认证与 Session Redis 化

> 状态：已完成（2026-08-21）。验收记录见《阶段3-认证与SessionRedis化验收记录》。

### 目标

将当前 JVM 内存 Session 切换到 Redis，支持服务重启和多实例部署。

### Redis Key 设计

```text
auth:session:{token}
rbac:user:{userId}
rbac:project:{projectId}:user:{userId}
```

Session 数据建议包含：

```json
{
  "userId": 1,
  "authVersion": 1,
  "createdAt": "2026-08-21T10:00:00",
  "expiresAt": "2026-08-21T18:00:00"
}
```

### 工作内容

- 使用随机 Token 继续保持当前前端兼容性；
- 登录成功后将 Session 写入 Redis；
- 使用 Redis TTL 管理 Session 过期；
- Spring Security Filter 从 Redis 加载当前用户；
- 登出时删除 Redis Session；
- 用户禁用、改密或权限变更时递增 `authVersion`；
- 清理对应用户和项目权限缓存；
- 增加 Redis 序列化和异常处理；
- 增加多实例共享 Session 测试；
- 增加 Redis 不可用时的明确错误响应。

### 验收标准

- 服务重启后已登录 Session 仍有效；
- 两个后端实例可以共享同一登录状态；
- Redis TTL 到期后 Token 自动失效；
- 登出后 Token 立即失效；
- 禁用用户后旧 Token 无法继续访问；
- 权限变更后旧权限缓存被清理。

### 回滚点

- 通过配置开关保留临时内存 Session；
- Redis 切换异常时可以回退到单实例开发模式；
- 生产环境不允许静默回退到内存 Session。

## 9. 阶段 4：持久层迁移到 MyBatis-Plus

### 目标

将所有 JPA 实体和 Repository 迁移为 MyBatis-Plus Entity、Mapper、XML。

### 推荐迁移顺序

1. 用户与认证；
2. 项目与项目成员；
3. 需求与测试用例；
4. API 工作台；
5. 自动化项目、测试任务和执行记录；
6. 报告与 Allure；
7. AI 模型、Prompt、AI 任务和审计；
8. Jenkins 实例、凭证和 Pipeline 绑定。

### 每个模块的迁移步骤

1. 创建 MyBatis-Plus Entity；
2. 创建 `BaseMapper` 接口；
3. 将派生查询迁移为 `LambdaQueryWrapper` 或 XML；
4. 将分页查询迁移为 `Page<T>`；
5. 将软删除迁移为逻辑删除字段；
6. 保持 Service 方法签名不变；
7. 执行模块级单元测试和接口测试；
8. 删除对应的 JPA Repository；
9. 确认事务边界和并发更新行为；
10. 记录 SQL 与索引验证结果。

### 重点注意

- 不要直接把 JPA 查询逐句翻译成字符串 SQL；
- 简单条件使用 Lambda Wrapper；
- 多表关联、复杂统计和报告查询使用 XML；
- 分页查询必须验证总数和排序结果；
- 软删除、更新时间和乐观锁需要统一实现；
- 生产 SQL 必须避免全表扫描；
- 所有用户输入必须使用参数绑定，禁止字符串拼接。

### 阶段验收标准

- 全部业务 Mapper 可以正常运行；
- 原有 API 响应不发生非预期变化；
- 分页、排序、过滤和统计结果与迁移前一致；
- 事务回滚行为保持一致；
- `pom.xml` 中移除 JPA/Hibernate 依赖；
- 项目中不再存在 `JpaRepository` 和业务 `@Entity`。

## 10. 阶段 5：权限治理与业务接入

### 目标

让所有受保护接口使用统一权限服务，不再依赖散落的角色字符串判断。

### 工作内容

- 实现系统级权限注解；
- 实现项目级权限校验；
- 将 `ProjectAccessService` 改造为基于权限编码判断；
- 迁移所有 `"ADMIN"`、`"MANAGER"` 等硬编码判断；
- 为用户、AI、Jenkins、项目成员接口增加权限控制；
- 为需求、用例、API、自动化和报告接口增加权限控制；
- 统一处理 Owner、管理员和项目成员的权限继承；
- 前端从“判断角色”逐步切换为“判断权限”；
- 增加无权限按钮隐藏和接口拒绝测试。

### 权限校验分层

| 层级 | 校验内容 |
| --- | --- |
| Spring Security | 是否登录、是否具备系统权限 |
| Controller | 接口级权限声明 |
| Service | 项目范围、资源归属和业务规则 |
| Mapper/数据库 | 数据范围和最终数据一致性 |

### 验收标准

- 每个受保护接口都有明确权限编码；
- 未登录返回 401；
- 已登录但无权限返回 403；
- 用户只能访问被授权的项目；
- 项目角色在不同项目之间互不串权；
- ADMIN 可以按设计访问系统级资源；
- 权限判断不再依赖前端传入的角色字段；
- 权限变更后 Redis 缓存及时失效。

## 14. 风险与应对

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| JPA 查询迁移遗漏 | 功能缺失 | 阶段 0 建立完整 Repository 清单 |
| JPA 与 MyBatis 事务行为不同 | 数据不一致 | 逐模块验证事务和回滚 |
| Redis 不可用 | 用户无法认证 | 增加健康检查、超时和告警 |
| 权限迁移错误 | 越权或误拒绝 | 使用权限矩阵和接口级测试 |
| 旧角色与新角色不一致 | 用户权限异常 | 保留兼容窗口并执行数据校验 |
| 复杂查询性能下降 | 页面响应变慢 | 使用 XML、索引和慢 SQL 分析 |
| 多实例 Token 不一致 | 登录状态异常 | 使用 Redis 共享 Session |
| 前端权限判断滞后 | UI 显示不准确 | 前端改为读取权限集合，后端最终校验 |
